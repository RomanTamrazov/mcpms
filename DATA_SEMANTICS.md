# Правила интерпретации телеметрии

Источник правил: ответы постановщика и переданный `справочник_состояний.csv`,
а также лист «Вопросы_нормализованные_и_Ответы» в
[таблице ответов постановщика](https://docs.google.com/spreadsheets/d/1xYVkEPm7PTiedfeobnrHl9EXlgq3766_/edit?gid=1030141402#gid=1030141402)
от 23.09.2026. Копия справочника, использованная проектом, находится в
`ml_service/reference/state_catalog.csv`.

## Подтверждённые правила

- `ид_канала_данных` — история одного конкретного параметра, сигнала датчика
  или инженерной системы.
- В одном канале могут появляться числовые измерения и текстовые состояния:
  некоторые устройства совмещают несколько функций.
- Число газового датчика — объёмная доля метана, `% CH₄`. Порог тревоги —
  **1%**. Диапазон **5–15%** приведён постановщиком как справочный диапазон
  возможности воспламенения, а не как новый порог модели.
- `01.01.1970 03:00:00` и `01.01.1970 03:00:01` — сбой даты; их нужно
  считать неисправностью, а не бинарным измерением.
- Отрицательные и аномальные числовые значения трактуются как неисправность.
  Для процентной доли метана значения за физическим диапазоном 0–100% также
  не являются валидным измерением.
- Текстовые состояния, их тревожность и технические значения берутся из
  справочника состояний. Техническое состояние не является числовым
  измерением.

## Проверка на архиве 2026

Проверен `ext-journal-2026.csv` из предоставленного архива: 30 695 389 строк.

| Наблюдение | Результат |
| --- | ---: |
| Значений `1970-01-01 03:00:00/01` | 6 951 |
| Тип этих значений в переданном каталоге каналов | только «Состояние охраны» |
| Числовых показаний газовых датчиков | 24 629 165 |
| Медиана / 99-й перцентиль метана | 0,01% / 0,19% |
| Показаний метана ≥ 1% | 5 419 |
| Показаний метана ≥ 5% | 2 |
| Показаний метана > 100% | 1 (327,68; неисправность) |

В архиве встречаются 5 993 184 текстовых значения. Совпадение по паре
`тип_датчика + название_состояния` со справочником есть только для 224 673
строк. В справочнике также есть противоречие: для пары «Газовый датчик» /
«Температура ниже 3ºC1» одновременно указаны `тревожное=true` и
`тревожное=false`.

Постановщик уточнил 24.09.2026: справочник состояний стыкуется с журналом по
`тип_датчика`, а не по конкретному `ид_канала_данных`. Поэтому для уникальной
пары `тип_датчика + название_состояния` каталог задаёт корректную тревожность.
Например, для «КД АВ» состояние «Обнаружен дым» тревожное, а «Дыма нет» —
нет; «КД АВ» объединяет наборы состояний дыма и движения. Исходный флаг
`тревожное` сохраняется для аудита. Конфликтующие и отсутствующие пары нельзя
угадывать: они остаются `ambiguous` и `unknown`.

## Что применено в проекте

`ml_service/telemetry_semantics.py` нормализует одно сырое значение в явном
виде: измерение, состояние или неисправность. Он:

- помечает обе даты 1970 как `quality=invalid`;
- возвращает единицу `% CH₄`, порог 1% и физический диапазон для газового
  датчика;
- возвращает тревожность из справочника для уникальной пары типа и состояния;
- сохраняет неоднозначность справочника как `quality=ambiguous`.

Проверка модуля:

```bash
cd ml_service
python telemetry_semantics.py \
  --state-catalog reference/state_catalog.csv \
  --sensor-type "Газовый датчик" --value 1.00
```

## Улучшения моделей без утечки

Новые правила полезны, но менять вход уже обученной модели без повторного
обучения нельзя: это даст иной распределение признаков на проде, чем на
временном тесте.

1. **Пожарный риск.** При следующем обучении добавить только прошлые на момент
   прогноза признаки качества дымовых/совмещённых каналов: число эпизодов
   `1970`, доля технических состояний, доля валидных измерений и число
   разнородных наборов состояний. Сохранить цель как новое срабатывание
   «Обнаружен дым» после разрыва >24 часов. Это улучшает устойчивость, но не
   превращает прокси-цель в подтверждённый пожар.
2. **Износ инфраструктуры.** Самый перспективный эксперимент — добавить к
   существующим 33 признакам канал-часа `fault_1970_count`,
   `invalid_numeric_rate`, `technical_state_rate` и
   `mixed_measurement_state_rate` за прошлые 24 часа/7 дней. Отбирать их
   только на временных фолдах и переобучать вместе с текущей витриной.
3. **Несанкционированный доступ.** Текущая цель уже узкая и корректная:
   только «Обнаружено движение» или «Не замкнут». Не следует переименовывать
   1970 или «Неисправен» во вторжение. Их можно добавить как отдельные
   технические признаки после повторной временной валидации; в текущем
   production-пайплайне они не меняют оценку предобученного ансамбля.

Для каждого эксперимента нужны те же календарные train/test-разрезы и
одновременная проверка Precision > 0,7 и Recall > 0,5. Порог выбирается только
на предшествующем валидационном отрезке, а не на тесте.

## Уточнения постановщика, важные для моделей

- Отдельной разметки подтверждённых инцидентов, ложных срабатываний и ремонтов
  не будет: журнал ОДС ведётся в отдельном help desk и не связан ключом с
  телеметрией. Поэтому все три подключённые цели остаются прокси-целями.
- Технические коды производителя, например `-100` и `255`, нужно игнорировать
  или учитывать как технические аномалии. Исторический 2021 год рекомендовано
  исключить: всплеск тревог возник при переходе на новую систему мониторинга,
  когда тревоги не снимались во время профилактики.
- Обновлённый справочник каналов содержит `ид_объект`; это разрешённый ключ
  для объектных и соседних признаков. Историческая геометрия не будет выдана:
  на сайте допустима наглядная условная линейная схема с пикетами.
- Данные о ремонтах, оборудовании и графиках горячих работ отсутствуют и не
  появятся. Открытые источники разрешены, но только с датой публикации до
  момента прогноза и с документированной привязкой к объекту/времени.
- Целевые Precision 0,7, Recall 0,5 и 24 часа — ориентиры по умолчанию, не
  жёсткие конкурсные пороги. Их сохраняем внутренними guardrail-метриками;
  изменение требуется обосновать в MVP.

Следствие для следующего обучения: новые признаки качества данных нужно
строить из прошлых наблюдений и оценивать на временных фолдах. Нельзя выдавать
технический код за подтверждённую поломку, а тревогу охранного или дымового
канала — за подтверждённое происшествие.

## Изменения для сайта и API

Передавать в карточку телеметрии `value_kind`, `quality`, `quality_reason`,
`unit` и `threshold`. Интерфейс должен показывать «неисправность/данные не
использованы» вместо отображения 1970 и 327,68 как обычных датчиковых
показаний. Скор пожарной и охранной моделей остаётся прокси-риском, а не
вероятностью подтверждённого происшествия.
